# m23244 — m20707 Beverloo verification: are its published numbers backed by tracked artefacts?

Predeclared **before** the re-run was inspected (written 2026-11-16, job `cj4709` still
`queued`).

## Decision to support

Is the verification note of mission m20707 (`docs/m20707_beverloo_verification.md`, the
deliverable set merged in `b2a67b44`) **evidence-backed** — i.e. do the published rates
reproduce from a fresh run, and are the artefacts they come from actually in the
repository — and if not, what is the minimal fix?

## Competing alternatives

* **A — status quo.** The note states that every number is "regenerated by `analyse.py`
  from the committed per-case artefacts in `benchmarks/m20707_beverloo/results/`".
  No such file is tracked by git (`results/` is in `.gitignore`), so the claim is
  currently unverifiable by anyone but the author.
* **B — reproduce + bind.** Re-run the `pilot` preset from the current `main`, commit the
  per-case artefacts to a path git actually tracks, render §3–§5 of the note from those
  artefacts (`analyse.py --inject-doc`) and make a test fail if note and artefacts
  disagree. Published numbers stay as published **iff** they reproduce.
* **C — retract.** If the re-run does not reproduce the published rates, mark the note
  `WITHHELD` and remove the numbers instead of defending them.

Decision rule: take **B** if the reproduction test below passes; take **C** for any case
that fails it (per case, not globally).

## Hypothesis

`tensordem.silo_flow` is a deterministic single-threaded numpy integrator with a fixed
seed, so the `pilot` cases reproduce their published rates to the printed precision when
re-run from the same code. The defect is therefore one of *bookkeeping* (artefacts never
survived `.gitignore`), not of numerics.

## Outcome metrics and unit of analysis

Unit = one case of the `pilot` preset (6 cases: `D4`, `D5`, `D5_g4`, `D5_mu40`,
`D5_mu55`, `D6`).

| metric | definition | baseline / control |
|---|---|---|
| `ΔW` | `(W_new − W_doc) / W_doc` of the steady mass-flow rate | `W_doc` = value printed in the merged note (§3 Table 1) |
| verdict flip | does `D5` keep `|W − W_Beverloo| / W_Beverloo < 10 %` | predeclared 10 % band, unchanged |
| traceability | `git check-ignore <artefact>` is non-zero for every committed artefact | current state: ignored |
| doc↔artefact agreement | `analyse.py --check-doc` exit code | currently: no such guard exists |

## Predeclared thresholds (fixed before inspecting the re-run)

1. **Reproduced**: `|ΔW| < 0.1 %` for all six cases → published numbers stand, they are
   re-labelled with the new artefact fingerprint.
2. **Variance-level drift**: `0.1 % ≤ |ΔW| < 5 %` on any case → the note's digits are
   *not* reproducible as printed; they must be replaced by the re-measured values and the
   window scatter (CV) must be reported next to them.
3. **Falsified**: `|ΔW| ≥ 5 %` on the primary case `D5`, or the 10 % verdict flips →
   honest FAIL: the note's verdict is retracted to `WITHHELD` and the discrepancy is
   reported, not tuned away.
4. **Traceability**: PASS iff every artefact cited by the note is committed and
   `git check-ignore` returns non-zero on all of them.
5. **Guard has teeth (mutation test)**: perturbing one digit inside a generated block of
   the note makes `--check-doc` / the pytest guard fail.

No threshold is adjusted after seeing the results; the 3 % / 10 % bands of the physics
comparison are the ones already predeclared in `analyse.py` (`TOL_REL` etc.).

## Variables

* **Controlled (must not change):** code revision of `tensordem.silo_flow`, campaign
  parameters (`BASE_PILOT`, `CASES_PILOT`), seed 20707, protocol
  (settle 0.03 s with plugged orifice, discard 0.05 s, 4 windows × 0.08 s, rate = mean of
  the last 50 % of windows), numpy/matplotlib versions on the executing node, reference
  coefficients from `benchmarks/m20055_beverloo/ref_beverloo_1961.json` (C = 0.58,
  k = 1.4).
* **Changed:** nothing physical. The only change is where the output lands
  (`benchmarks/m20707_beverloo/results/pilot/`, now git-tracked) and that the note is
  rendered from it.
* **Confounders / nuisance variables:** float64 reduction order (numpy `sum` over
  particle arrays) is deterministic for a fixed array layout; node CPU/BLAS differences
  can in principle perturb the last bits, which is why threshold 1 is 0.1 % and not
  exact equality. Window-scatter statistics (4 windows, mean of the last 2) are *not*
  reduced by re-running the same seed — they are the irreducible noise of this preset and
  are reported as `CV` in both runs.

## Repetitions

Re-run each case once: the run is deterministic by construction (fixed seed, no wall
clock, no stochastic thermostat), so a second identical run adds no information. The
noise estimate is taken from the *within-run* window scatter (4 windows per case), which
is the quantity that limits the published accuracy claim. Repetition rationale recorded
here rather than assumed.

## Interpretation limits

* Agreement at the pilot preset (1140 particles, k_n = 2 kN/m, 4 windows) constrains the
  *bookkeeping* claim ("these numbers come from these artefacts"), not the *physical*
  claim of 3 %-level Beverloo agreement: the window scatter of this preset (CV 0.02–1.09)
  is larger than a 3 % band. The physical verdict stays as predeclared in `analyse.py`
  (10 % band) and stays honest if it fails.
* The `full` preset (d = 3 mm, 6 cases, ≈ 50 min/case) remains outside this mission's
  budget; its status stays `WITHHELD` and is now *rendered* as such instead of being
  asserted by hand.
