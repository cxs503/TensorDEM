# PR 修红：TensorDEM #189 / #190 / #191 / #193（m3814）

## 1. 结论先说

四张 PR 的 `unit-tests` 红**同根**，不是四份独立的物理/数值缺陷：

| 根因 | 触发条件 | 影响 PR | 修法 |
|---|---|---|---|
| **R1 主干漂移（共同）** | 分支基点早于 main 的 `scipy>=1.10` 依赖（该依赖由 PR #203 / m3317 落到 main），而分支所带的测试在 collection 阶段就 `from scipy import sparse`、`from scipy.optimize import minimize` | #189 #190 #191 #193 全部 | 把当前 `origin/main` 合入分支，使分支自带依赖声明；PR 的 merge tree 不再依赖主干偶合状态 |
| **R2 共享测试断言脆弱（共同）** | `tests/test_threefield_lbm_transport.py::test_streaming_is_mass_conserving` 用**绝对** `1e-12` 判据，而被输运质量 `Σf = 1.6490e4` | 本地复现于 #190 #193 的合并树 | 改为相对判据（相对被输运质量） |
| **R3 分支局部（仅 #193 / m3267）** | `tests/test_ridge_dem_core_physics.py::test_recommended_dt_elastic_limit` 只断言弹性极限，但该组参数下**粘性极限更紧**，实现返回 `min(elastic, viscous)` | #193 | 拆分两个极限：弹性分支用弱阻尼参数、另加一条 `min()` 不变量用例 |

CI 日志原始证据（GitHub Actions 失败 job 日志；当时的取日志脚本 `ci_logs.py` 未进入仓库，下列命令按本 RCA 记录复现即可）：

```
$ gh run view --job <job-id> --log   # 拉四张 PR 的失败 job 日志
=== PR #189  log=/tmp/ci_log_m189.txt
! ERROR collecting tests/test_dem3d_born_huang.py ...
E   ModuleNotFoundError: No module named 'scipy'
... 6 errors during collection ... Interrupted
```
四张 PR 的失败点**完全同形**：`pip install -e ".[test,viz]"` 装出的环境里没有 scipy
（`Successfully installed ... tensordem-0.1.0 torch-2.14.1 ...`，scipy 缺席），
于是 pytest 在 **collection** 阶段就中断，一条用例都没跑 —— 这也解释了为什么
四张 PR 的失败报告长得一模一样。

## 2. 怎么做的

1. **复现**：不改动任何分支，先用 `git merge-tree --write-tree <main> <branch>`
   在对象库里算出 GitHub 会给 CI 用的**合并树**，再 `git archive` 导出到 `/tmp`
   跑全量 `pytest`（`conftest.py` 已把本树 `src/` 插到 `sys.path` 首位，故不受
   其它 worktree 的 editable install 干扰）。
2. **判别同根**：把 GitHub 失败 job 日志逐条比对 → 四条 `ModuleNotFoundError: scipy`
   一致；再 `git log -S"scipy>=1.10" -- pyproject.toml` 定位到主线引入该依赖的提交
   （m3317 / PR #203），确认四张 PR 的 CI 运行时间早于它。
3. **同根同法批量修**：四张分支各把 `origin/main` 合入（无冲突，`merge-tree`
   与本地 `git merge` 均返回 0），依赖声明随分支走。
4. **独立失败逐张修**：
   * R2 → 相对判据（四张都改，属共享测试文件）；
   * R3 → 只改 #193。
5. **验证**：修订前后同一合并树上跑同一用例；并用解析量核对断言阈值是否落在
   浮点可分辨范围内（见 §4 误差判定）。

## 3. 关键数字（程序化取自实测，零手抄）

R2 的失败现场（`/tmp/pt_m3201.log`，修订前）：

```
assert 3.637978807091713e-12 < 1e-12          # 实测 |Σf_stream − Σf| = 3.638e-12
sum(periodic_stream(f)) = 16490.1761          # 被输运质量 O(1e4)
```

浮点可分辨性核算：

* `float64` 机器精度 `eps = 2.220446e-16`；
* 该总量的 1 ulp = `eps * 2^ceil(log2(16490)) = 2.2204e-16 * 16384 ≈ 3.64e-12`
  —— **实测偏差恰好等于 1 ulp**，即“仅求和次序不同”；
* 断言阈值 `1e-12` 只及 0.27 ulp，**低于被比较量自身的可表示分辨率**，
  任何保质量的实现都只能靠 BLAS/线程归约次序的运气过关。

R3 的失败现场（`/tmp/pt_m3267.log`，修订前）：

```
0.0002209233484157853 != 0.00033286867723229607   (差 1.119e-4)
```
按 `ridge_dem.py:176-185`：

* `mass = ρ π r² = 917·π·0.5² = 720.20 kg`（二维圆盘、单位厚度）；
* `stiffness = 13·(k_c + 2k_b) = 13·(1e7 + 1e7) = 2.6e8 N/m`
  → `dt_elastic = 0.2·sqrt(m/k) = 3.3287e-4 s` ← 测试原期望值；
* `damping = 13·c_d + drag = 13·5e4 + 2e3 = 6.52e5 N·s/m`
  → `dt_viscous = 0.2·m/damping = 2.2092e-4 s` ← **实现实际返回值**；
* `recommended_dt = min(elastic, viscous) = 2.2092e-4 s`，实现正确、**测试期望漏了下限**。

## 4. 误差判定（逐项，显式回答是否 <3%）

| 量 | 基准 | 修订前 | 修订后 | 相对误差 | <3%? |
|---|---|---|---|---|---|
| 周期 stream 质量守恒 `|ΔΣf|` | 精确守恒（streaming 是沿特征线的精确置换） | 3.638e-12 绝对（=1 ulp），被 `1e-12` 绝对判据误判为红 | 相对 2.21e-16（≤ 1e-12 相对判据） | 2.2e-16 (相对) | **是** |
| `RidgeMaterial.recommended_dt`（强阻尼组） | 手算 `min(0.2√(m/k), 0.2m/c) = 2.20923e-4 s` | 测试期望 3.32869e-4 s（错取弹性极限） | 与实现/手算一致 | 0（同一表达式，`places=12`） | **是** |
| `RidgeMaterial.recommended_dt`（弱阻尼组，新增用例） | 手算 `dt_elastic = 3.3287e-4 s`，且 `dt_elastic < dt_viscous = 1.10e-2 s` | — | 实现返回值 | 0 | **是** |

结论：三项关键量的判定误差都在 **1 ulp / 0** 量级，**均远小于 3%**；
不存在“为绿而绿”的放宽——相对判据 `1e-12` 仍比任何真实的质量泄漏（周期性盒内
一个坏 stencil 造成的泄漏是 O(1e-3) 相对量级）严 9 个数量级。

## 5. 注意点 / 局限

* **本机 torch 与 CI 不同版本**（本机 2.7.1，CI 钉 `torch==2.14.1`）。R2 的临界偏差
  正是随归约次序浮动的量，因此本机能否复现红不代表 CI；但**判据本身的缺陷与实现无关**：
  阈值低于 1 ulp 时任何实现都可能随机红，故按相对量修是唯一稳健解。
* R1 的正确归宿是“分支自己声明它 import 的第三方依赖”。本次选择合并 main 而不是
  在分支里再写一遍 `scipy>=1.10`，因为合并后两者文本一致、且顺带消除了 300+ 文件的
  长期漂移（合并后 PR diff 只剩本分支独有改动）。
* 6 条 `ERROR`（`tests/test_doc_evidence_pointers.py`）是**本机导出目录不是 git 仓库**的
  产物（`git -C … ls-files` 返回 128），CI 真实检出下不出现，未做任何改动。
* 合并树全量套件在本机运行受宿主负载影响（load average 一度 >3000），#189/#191 的
  全量跑到 97–98% 时用例仍在跑；已单独跑通各自受影响用例，但**未拿到 100% 套件的
  完整绿票**，故诚实标注为“未完全验证”，最终以 PR CI 为准。
