# TensorDEM verification-debt register

Purpose: a durable, honest list of *known evidence gaps* in TensorDEM, each with
what is missing, how it was detected, what a single agent could do about it, and
what blocks it. It exists so that self-directed work does not re-discover the same
gaps and does not convert them into false claims.

Detection instrument: `docs/verification-evidence/verification_ledger.json`
(generated by `scripts/audit_verification_evidence.py`). Every entry below cites
either a ledger field, a source file and line, or a document section that was read.

Status vocabulary: `OPEN` (nothing done), `PARTIAL` (instrument or partial
evidence exists), `BLOCKED` (cannot be closed with the evidence available in this
repository), `CLOSED` (evidence now exists, with a pointer).

| id | debt | status | blocked by |
| --- | --- | --- | --- |
| D1 | MT Uikku formula baselines are transcribed numbers, not implemented formulas | `BLOCKED` | ship particulars absent from repo, no network |
| D2 | 8 quantitatively tested modules are never named in `docs/` | `OPEN` | writing effort only |
| D3 | 37 of 45 modules have only file-level test attribution | `OPEN` | mechanical test edits |
| D4 | No numeric acceptance threshold for ice resistance vs experiment | `OPEN` | needs a declared engineering use case |
| D5 | Ledger records evidence *style*, not execution results | `PARTIAL` | CI runtime cost |
| D6 | Channel-ice (broken-ice) cases absent from the validation dataset | `BLOCKED` | source table not transcribed |

## D1 — The "formula baselines" benchmark contains no formula

**Claim under audit.** `docs/dem3d_mt_uikku_formula_baselines.md` and
`scripts/benchmark_dem3d_ship_ice_formula_baselines.py` present scores for
Lindqvist, Riska, Jeong and Keinonen against the MT Uikku Table 8 reference.

**What the code actually does.** `scripts/benchmark_dem3d_ship_ice_formula_baselines.py`
defines `FORMULAS` as a mapping from *CSV column names* to display names and then
reads those columns:

```python
FORMULAS = {
    "lindqvist_prediction_kN": "Lindqvist",
    "riska_prediction_kN": "Riska",
    "jeong_prediction_kN": "Jeong",
    "keinonen_prediction_kN": "Keinonen",
}
```

No formula is evaluated anywhere in the file: there is no ice-thickness, flexural
strength, speed, friction or hull-geometry arithmetic. The metrics are therefore a
**scoring of transcribed literature values**, which is a legitimate reference-data
audit (the module docstring says so) but is *not* a reproduction of the formulas
and cannot detect a transcription error in those four columns.

**Why this matters.** As written, TensorDEM cannot compute a formula baseline for a
case that is not already in the CSV — a different ship, a different ice thickness, a
channel-ice case, or a DEM run that needs a like-for-like empirical comparison. It
also cannot check the four transcribed columns for consistency.

**What would close it.** Implement Lindqvist (1989) and Riska (1997) as code with an
explicit `ShipParticulars` input (length, beam, draft, displacement, bow/stem
angles, hull–ice friction) and reproduce the Table 8 columns within a declared
tolerance.

**Why it is blocked here.** Lindqvist and Riska both require full-scale hull
particulars and bow angles. This repository contains only ice properties and
resistance values; `benchmarks/dem3d/ship_ice_validation/README.md` states that the
source article reports them, but they are not transcribed. Re-deriving them from
resistance values would be curve fitting, and transcribing them from memory would
violate the "no untraceable numbers" rule. Network access to the open-access article
(DOI 10.1016/j.ijnaoe.2016.01.004) is blocked in this environment.

**Safe partial step (still useful, not done here).** Add the parametric
`ShipParticulars` API with unit tests on analytic limits (resistance vanishes with
ice thickness, static term retained at zero speed, linear in beam), so that the only
missing pieces are cited literature constants. Deliberately not done in this
increment: an implementation whose coefficients cannot be checked against the source
would look like `REAL` evidence while being unverified, which is worse than an
explicit gap.

## D2 — Quantitatively tested modules that no document names

From the ledger (`grade == QUANTITATIVE_UNDOCUMENTED`): `buoyancy_verification`
(17 tests), `cli` (38), `dem3d_lattice_elastic` (30), `dem_export` (18),
`lattice_waves` (12), `continuum_boundary_dem` (5), `calibrated_wet_coupling` (2),
`moving_plane_boundary` (2).

Note this is a **documentation-traceability** debt, not a test debt: several of these
do have prose documentation (`docs/dem3d_lattice_wave_propagation.md`,
`docs/dem3d_lattice_elasticity3d_audit.md`) that never writes the module name, so a
reader cannot walk from the claim to the code. The ledger matches module *names*.

**Single-agent scope.** For each listed module, add one line naming the module in
the relevant `docs/*.md`, or add a one-paragraph module note. No code change. Gate:
the module becomes `QUANTITATIVE_DOCUMENTED` in the regenerated ledger.

## D3 — Most evidence is attributed at file level

The ledger reports 8 modules with `direct` attribution and 37 with `file`
attribution. File-level attribution means the module name appears in the test file
but not in the individual test function bodies — typically because tests call
`from tensordem.x import Class` once and then use `Class`. Consequences: a grade can
be produced by *any* test in that file, so the grade is a weaker statement than it
looks.

**Single-agent scope.** In each test file, qualify a representative call with the
module path (for example `tensordem.lattice_waves.dispersion(...)`) so that the
module is named in the body. Gate: `direct_test_count > 0` for the module and the
grade unchanged. This raises confidence without changing physics.

## D4 — No acceptance threshold for ship–ice resistance

`benchmarks/dem3d/ship_ice_validation/README.md` proposes a "practical first
screening" of MAPE <= 25 % but explicitly does not impose it, and the platform
standard for this ecosystem is 15 % on key quantities. No TensorDEM run currently
produces a resistance comparison to be thresholded at all, so the threshold cannot
be evaluated.

**Single-agent scope.** Declare the threshold and the uncertainty budget *before*
running the case, in a pre-registration document, then report the measured value
against it. Do not retro-fit a threshold to a finished run.

## D5 — The ledger is static; execution results are not in it

A module graded `QUANTITATIVE_DOCUMENTED` could have failing or skipped tests. The
audit deliberately stays static (about one second, no imports), because running 999
test functions is minutes of CPU and this repository's heavier suites need real
compute.

**Single-agent scope.** Add a second, optional stage that runs a caller-selected
subset (`-k`) and joins pass/fail into the ledger as an extra column, keeping the
static ledger authoritative for style and the dynamic run authoritative for outcome.
Gate: the joined file is reproducible and the static ledger is byte-identical when
the dynamic stage is absent.

## D6 — Channel-ice cases are missing from the dataset

`benchmarks/dem3d/ship_ice_validation/README.md` warns that Tests 304–306 and
404–406 are broken-ice channel cases that must not be mixed into the level-ice set;
the CSV contains only the ten level-ice cases. Anything called "ice resistance
validation" therefore covers level ice only.

**Blocked by.** The channel-case table values are not transcribed, and the source
article is not reachable from this environment (see D1). Do not infer these values.

## Maintenance

- Append new entries; do not silently delete a debt. Close with a pointer
  (`commit`, `report id`, `ledger field`) and keep the rationale.
- Regenerate the ledger after changing tests or docs; the committed JSON is checked
  against a fresh run by `tests/test_audit_verification_evidence.py`.
- A debt with no owner is not a plan: give each entry a scope small enough for a
  single agent to finish and verify.
