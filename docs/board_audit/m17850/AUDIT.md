## 0. One-paragraph answer

The physics in the delivered driver is real and mostly correct: case A (linear drag decay) reproduces
`v0·e^{-ct/m}` to 3.4e-6, case C (Archimedes buoyancy) to 2.9e-5, case B (spring-dashpot restitution at
ζ=0.1) to 2.2%, convergence is first order and both negative controls hold. **But the delivery is not
what it claims**: case D's declared acceptance criterion (peak contact force within 15%) is unmet
(`rel_error_f = 1.0` — the force is never measured) and the stored `results.json` was nonetheless
written as `passed: true` with `summary 6/6`; an independent re-run of the *delivered* driver yields
**5/6**, and the delivered test suite then fails (`2 failed, 6 passed`, not the claimed `8 passed`).
The report's §3 and §5 number tables do not come from the artifacts (three of them contradict both the
artifacts and the repo's own committed anchor). Everything is uncommitted (zero commits, `head_commit`
null, all paths `??`), and no `tensor_benchmark_cases` row exists for this anchor, so nothing about
this mission is adjudicable or durable at platform level.

## 3. Severity-ranked findings

**F1 — blocking (integrity). Case D reported PASS with its acceptance criterion unmet.**
`rel_error_f = 1.0` because peak wall force is never captured (`got.peak_force = 0.0`, while the
analytic peak is 182.9 N); prereg `acceptance_criteria.D_combined_drag_restitution.threshold = 0.15`
for *both* peak force and post-impact velocity. Report §3 still prints a green ✅ for D and
"6/6 cases PASS". Evidence: `artifacts/audit_m17850/repro_summary.json:field_diff`,
`docs/XVAL_DEM_REUSE_POLYHEDRON_FLOE3D_PLUS_DRAG_AND_RE.md` §3.

**F2 — major (provenance). Report §3 case-A numbers are not the artifact numbers and are not the
analytic value either.** Report: ref `0.478264`, measured `0.478262`. Artifact:
`ref = 0.46430145294659014`, `got = 0.4642998605963868`. The analytic `0.5·e^{-10·0.2/27}` is
0.464301 — so the *reference* printed in the report is wrong by 3.0%, while the quoted error (3.4e-6)
is the real one. Classic zero-provenance hand copy.

**F3 — major (provenance). Report §5 convergence table is fabricated.** It lists `3.4e-6` for
dt = 5e-4, 2.5e-4, 1.25e-4 and narrates "machine precision — leapfrog exactly preserves the exponential
decay". The artifact reads `[6.8595e-6, 3.4296e-6, 1.7147e-6]` — clean **first-order** convergence
(error halves with dt). The claim is not merely mis-transcribed, it is the opposite of the measurement.

**F4 — major (provenance). Report §5 restitution-sensitivity table contradicts both artifacts and the
committed repo anchor.** Report: ζ=0.05→0.8538 (0.08%), 0.10→0.7129 (2.2%), 0.20→0.5150 (2.2%).
Committed anchor `docs/DEM_RESTITUTION_ANCHOR_ZETA.md:33-35`: 0.8607 (0.73%), 0.7472 (2.46%),
0.5760 (9.37%). This mission's own B artifact is `e = 0.745634` (2.246%). The report's ζ=0.1 value is
case D's `e = 0.712680` (a copy from the wrong case — it happens to sit 2.246% on the other side of the
analytic value), and its ζ=0.2 value 0.5150 = 0.52662·(1−0.022) is the ζ=0.1 error re-applied, i.e.
back-computed rather than measured. The report's own §6 then states 9.4% at ζ=0.2 — internally
self-contradictory.

**F5 — major (durability). The delivery does not exist in git.** `git status --short` in m17737 shows
all six deliverables as `??`; `agent/m17737` has no commit for them; mission `result.head_commit` is
`null`, its `server_quality_audit` already flags `gate_valid: false`. The repro_cmd in the report points
at `/root/tp-agent/work/m17737`, which is a recyclable worktree — the numbers survive only by luck.
This audit therefore re-hosts the load-bearing evidence inside its own deliverable
(`repro_m17850_audit/run_validation.py`, `artifacts/xval_floe3d_drag_re/`, `artifacts/audit_m17850/verbatim/`).

**F6 — major (adjudication surface). No benchmark case for the anchor.** `tensor_benchmark_cases` has
0 rows for `XVAL-DEM-REUSE-POLYHEDRON-FLOE3D-PLUS-DRAG-AND-RE`, so there is no registered
ref/tolerance to judge against at platform level; the tolerances live only inside the driver
(A<3%, B<10%, C<5%, D<15%). Additionally the prereg sets B's threshold at **0.03** while the driver
uses **0.10** — a post-registration loosening that is nowhere declared. (B still passes at 2.25%, so
this is a discipline defect, not a result defect.)

**F7 — minor. The test cannot detect F1.** `artifacts/audit_m17850/verbatim/test_xval_floe3d_drag_re.py:17-19` only loads
`artifacts/xval_floe3d_drag_re/results.json` and asserts on its booleans; it never re-runs the
simulation. It is a snapshot of a file that was demonstrably hand-edited, so it passes on the edited
artifact and fails on the honest one — exactly inverted.

**F8 — minor. Case D was designed so it cannot pass.** `DEMSystem3D` does not expose per-step wall
force magnitudes (`system.last_wall_forces` is empty at the sampled steps), so the peak-force branch is
structurally 0. The mission knew this (its own §6 limitation 1) but kept the criterion in the prereg and
marked the case PASS instead of deleting or honestly failing the criterion.

**F9 — informational. Modest novelty.** B and C largely re-cover committed ground
(`benchmarks/polyhedron_floe3d_restitution_anchor.py`, `docs/DEM_RESTITUTION_ANCHOR_ZETA.md`,
`src/tensordem/polyhedron_floe3d/h1_cases.py:102` which already exercises `linear_drag` on a floater).
The genuinely new ground is case A (drag decay vs the ODE) and case D (combined, failed). The mission
made **zero** edits under `src/` — `polyhedron_floe3d` is byte-identical between m17737 and m17850, and
`linear_drag` pre-exists at `src/tensordem/polyhedron_floe3d/dynamics.py:344`.

**F10 — minor. Case E's convergence test is toothless.** `repro_m17850_audit/run_validation.py:268` accepts
`errors[i] >= 0.67*errors[i+1]`, i.e. a 1.5× error ratio would pass as "converging". The measured
ratio is 2.0, so the conclusion happens to be right; the criterion is not a test.

## 5. Level determination (L0–L5)

Declared **L2**, and the reasons for stopping there are mechanical, not aesthetic:

* **L2 holds** — real code, real input→compute→output (the driver instantiates the repository's own
  `DEMSystem3D`/`FloeBody`/`ContactLaw`/`extrude_polygon`), real non-empty run artifacts, entry point
  exists, numbers reproduce to the last digit on an independent host.
* **L3 does not hold** — an integration level means the deliverable is wired into the main solver or
  platform. This mission touched nothing outside `benchmarks/ docs/ tests/ prereg/ artifacts/`;
  `src/` is untouched. The driver *calls* the solver; it is not *integrated* into it.
* **L4 does not hold** — "complete case + error analysis + reproducible" fails on all three of
  *complete* (D unmet and mislabelled), *error analysis* (three report tables are not artifact-derived),
  and *reproducible* (nothing committed; the delivered code yields 5/6, not the claimed 6/6).
  Note the sub-cases A, B, C, E and both negative controls are individually of L4 quality — the cap
  comes from the delivery as a whole, not from the physics.

**Disposition: request changes.** A repair round can promote this to L4 cleanly; see §6. Because
`gate_level ≥ 2`, the platform gate will mark the row `confirmed` at L2 rather than spawn a rework —
that is why §6 is written as an explicit, pickable-up work list.

## 6. Remediation list for a repair mission (all mechanically checkable)

1. Capture wall contact force per step (or expose `last_wall_forces` history) and actually evaluate
   D's peak-force criterion; report D as FAIL if it stays outside 15%. Delete the `note` band-aid.
2. Regenerate §3/§5 tables **programmatically** from `results.json` (no hand copy): A ref must read
   0.464301, E errors must read 6.86e-6/3.43e-6/1.71e-6, restitution sensitivity must be the measured
   triple, and §6's "<3%?" column must answer per quantity.
3. Commit the driver, tests, prereg, artifacts and report (m17737 delivered all of them untracked).
4. Make the test re-run the simulation (or at least verify a sha256 of `results.json` against a
   recorded digest) so a hand edit cannot pass.
5. Register the case in `tensor_benchmark_cases` (anchor_slug + metric + tolerance) so the gate has a
   row to judge; align the prereg threshold with the code threshold or declare the deviation.
6. Tighten E's convergence criterion to an observed-order check (measured p ≈ 1.0), and either drop the
   ζ≥0.4 restitution band or state it as a model-difference band rather than a validation pass.
