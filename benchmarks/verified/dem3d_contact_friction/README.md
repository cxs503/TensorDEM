# DEM3D contact-friction supplementary tables (mission m2520)

Manuscript-facing tables for **`paper-draft-tensordem-contact-friction`**: a 2-D
sensitivity scan of the contact/restitution/friction parameters, and convergence
tables for the Hertz contact kernel and the spherical-cap buoyancy kernel.

Everything here is generated by one script and written to CSV/JSON; no number in
this document was transcribed by hand (the tables below are the CSV content
reformatted, and `summary.json` carries the machine-readable verdicts).

| item | value |
|---|---|
| repository | `TensorDEM` (branch `agent/m2520`) |
| generator | `scripts/benchmark_contact_friction_tables.py` |
| command | `PYTHONPATH=src python scripts/benchmark_contact_friction_tables.py` (~4 min CPU) |
| base commit of the recorded run | `3ba5a1a6bbd18f11bbb35b120c447864d5fe03f5` (`summary.json:commit`) |
| environment | CPU, torch 2.7.1, float64 solver state as configured by `IceDEM3D` |
| verdicts | `benchmarks/verified/dem3d_contact_friction/summary.json` |

Reproduce a single table by importing the module and calling the matching
function, e.g.

```bash
PYTHONPATH=src python -c "import importlib.util as u; s=u.spec_from_file_location('t','scripts/benchmark_contact_friction_tables.py'); m=u.module_from_spec(s); s.loader.exec_module(m); rows=m.hertz_rows()[0]; m.write_csv(m.OUT_DEFAULT/'hertz_convergence.csv', list(rows[0]), rows)"
```

## Table 1 — restitution response over `(k_n, e)`

**File:** `benchmarks/verified/dem3d_contact_friction/restitution_kn_e_sweep.csv`
(30 rows = 5 stiffness x 6 target restitution; fixed `R = 0.05 m`, `rho = 900 kg/m^3`,
closing speed `v0 = 0.5 m/s`, equal-mass pair, `m_eff = m/2 = 0.23562 kg`).

**Method.** Two free particles collide head-on inside `IceDEM3D` (identical
construction to `contact_impact._build_pair`, driven through the only public
restitution route in this tree, `DEM3DConfig(restitution_coefficient=e)`). The
realised restitution is `|v_out|/|v_in|` of the relative normal velocity on the
first free-flight step after separation. Per point the table carries three
references:

* `e_ref_clipped_law` — exact solution of the engine's *own* clipped law
  `F = max(0, k_n d - c_n dn/dt)` at the damping the engine actually built
  (`restitution.unilateral_restitution`, event-localised RK4);
* `e_ref_bilateral_formula` — the textbook bilateral value
  `exp(-pi zeta / sqrt(1-zeta^2))` whose inversion produced that damping;
* `damping_c_corrected_Ns_per_m` + `damping_correction_ratio` — the damping that
  *would* realise the target under the clipped law
  (`restitution.damping_for_restitution`), and its ratio to the damping used.

**Result (selected rows, read from the CSV).**

| `k_n` [N/m] | `e_target` | `e_measured` | `e_ref_clipped_law` | rel. err vs clipped | rel. err vs target | `c_corrected/c_engine` |
|---|---|---|---|---|---|---|
| 2.0e+04 | 0.20 | 0.32943 | 0.32486 | +1.41 % | +64.7 % | 1.604 |
| 2.0e+04 | 0.50 | 0.55519 | 0.55028 | +0.89 % | +11.0 % | 1.185 |
| 2.0e+04 | 0.95 | 0.95158 | 0.95051 | +0.11 % | +0.2 % | 1.011 |
| 1.0e+06 | 0.20 | 0.32835 | 0.32486 | +1.07 % | +64.2 % | 1.604 |
| 1.0e+06 | 0.50 | 0.55431 | 0.55028 | +0.73 % | +10.9 % | 1.185 |
| 1.0e+06 | 0.95 | 0.95133 | 0.95051 | +0.09 % | +0.1 % | 1.011 |

**Verdict.**

* Against the *engine's own* law (the quantity the integrator must reproduce):
  max |error| = **1.41 %** over all 30 points, 0.89 % for `e_target >= 0.5`.
  **Within 3 % → PASS.**
* Against the *target restitution* the user asked for: max error **+64.7 %**
  (`k_n = 2e4`, `e = 0.2`). **NOT within 3 % → honest FAIL**, attributed to the
  known law mismatch: the engine inverts the *bilateral* mapping and then applies
  a *unilateral* (clipped) force, so the realised restitution is systematically
  high; the required damping correction is 1.01x-1.60x (larger at small `e`).
  The corrected mapping is available as `restitution.damping_for_restitution`
  /`contact_impact.restitution_to_damping_clamped`, but the solver in this tree
  exposes no input for an absolute `contact_damping` on the particle-particle
  branch (see "Limitations"), so the correction cannot be exercised end-to-end
  without a solver change that is out of scope here.
* Momentum drift is exactly `0` in every row (the pair branch conserves linear
  momentum).

## Table 2 — realised rolling-resistance / friction coefficients over `(k_n, e)`

**File:** `benchmarks/verified/dem3d_contact_friction/rolling_friction_kn_e_sweep.csv`
(240 rows = 5 `k_n` x 6 `e` x 2 parameter pairs `(mu, mu_r) = (0.40, 0.05)` and
`(0.05, 0.01)` x 4 incline angles `2, 4, 10, 20 deg`).

**Method.** The repository's single-sphere-on-an-incline harness
(`rolling_resistance.simulate_sphere_on_incline`, `cdt` rolling law, Cundall-Strack
tangential spring) is integrated at the same `(k_n, e)` pair as Table 1, with the
normal damping taken from the same bilateral mapping
(`gamma_n = 2 zeta sqrt(k_n m)`), 60 steps per elastic contact period, 0.10 s run,
steady fit over the second half. The measured slope acceleration is converted back
to coefficients (`mu_r_eff = tan(theta) - a(1+I/mR^2)/(g cos theta)`,
`mu_eff = tan(theta) - a/(g cos theta)`) and compared with the closed forms
`incline_rolling_acceleration` (rolling regime) / `incline_sliding_acceleration`
(sliding regime); the regime is decided per point by `pure_rolling_feasible`.

**Result.**

| incline angle | max abs rel. err a | regime |
|---|---|---|
| 20 deg | 1.43 % | rolling |
| 10 deg | 2.23 % | rolling |
| 4 deg | 5.00 % | rolling |
| 2 deg | 103.73 % | rolling (max abs err 0.110 m/s^2, `a_ref = -0.106 m/s^2`) |

* Recovered Coulomb coefficient in the sliding regime: `mu_eff` equals the
  declared `mu` to **2.6e-13** (machine precision).
* Maximum `|a|` error over the three dynamically meaningful angles: **5.00 %**
  (`k_n = 2e4`, `e = 0.2`, `mu = 0.4`, `mu_r = 0.05`, `theta = 4 deg`);
  `10 deg` and `20 deg` are inside 3 %.
* The `2 deg` column is *not* a valid relative-error target: it sits just below
  the static threshold, so the reference acceleration is a small difference of
  two comparable terms (`g(sin2 - 0.05 cos2)/1.4 = -0.106 m/s^2`) and the
  relative error is dominated by the noise floor of the steady fit. It is kept in
  the CSV for completeness and excluded from the verdict.

**Verdict.** Friction: **PASS** (exact clamp). Rolling resistance: **2 of 3
dynamic angles < 3 % (PASS)**, the near-threshold `4 deg` point is **5.0 % →
honest FAIL** at the 3 % band, attributed to the proximity of the incline angle
to the rolling/sliding threshold where the residual acceleration is a small
difference of order-`mu_r` terms (a 5 % acceleration error is only +7e-3 m/s^2,
i.e. about 2 % of the rolling-resistance torque). The `(k_n, e)` dependence of
both coefficients is weak: `mu_eff` is `k_n`/`e`-independent by construction (the
Coulomb clamp is a static bound), and `mu_r` shows no systematic drift with
`k_n` or `e` beyond the angle-dependent deltas above.

**File:** `benchmarks/verified/dem3d_contact_friction/friction_kernel_conformance.csv`
(9 rows = 3 `k_n` x 3 `mu`) — static conformance of the Cundall-Strack clamp
inside `IceDEM3D`: `|F_t|/|F_n| = mu` to **2.2e-16** at every point.

## Table 3 — Hertz contact-kernel convergence (3 contact-scale levels x 5 dt)

**File:** `benchmarks/verified/dem3d_contact_friction/hertz_convergence.csv` (15 rows).

**Method.** The Hertz law `F = (4/3) E* sqrt(R*) d^(3/2)` is point-local: it has
no spatial mesh, so the "3 levels" are the three contact scales a timestep
criterion must cover (`E* = 0.1, 1, 10 GPa` at `R* = R/2 = 0.025 m`), and the
5 levels are `dt = t_c/10 ... t_c/160`. The kernel is integrated with the same
semi-implicit Euler update the DEM solver uses, with the exact closed forms

```
K      = (4/3) E* sqrt(R*)
d_max  = (15 m v0^2 / (16 K))^(2/5) = (5 m v0^2 / (4 K))^(2/5)
F_max  = K d_max^(3/2)
T_c    = 2.943275 (15 m / (16 E* sqrt(R*)))^(2/5) v0^(-1/5)
         = 2.868492 (m^2 / (R* E*^2 v0))^(1/5)          [same value, two normalisations]
```

The coefficient `2.943275 = 2 * sqrt(pi) |Gamma(0.4)| / ... ` is computed here from
`math.gamma`, not transcribed: `2 * B(0.4, 0.5) = 2.943275`,
`B(0.4,0.5) = Gamma(0.4)Gamma(0.5)/Gamma(0.9)`.

**Result.**

| steps per `t_c` | `dt` [s] (E*=1 GPa) | rel. err `d_max` | rel. err `F_max` | rel. err `t_c` |
|---|---|---|---|---|
| 10 | 9.708e-05 | +5.80e-03 | +8.72e-03 | -5.58e-03 |
| 20 | 4.854e-05 | +1.35e-03 | +2.02e-03 | -1.34e-03 |
| 40 | 2.427e-05 | +3.20e-04 | +4.80e-04 | -3.29e-04 |
| 80 | 1.213e-05 | +7.71e-05 | +1.16e-04 | -8.15e-05 |
| 160 | 6.067e-06 | +1.88e-05 | +2.82e-05 | -2.02e-05 |

* Observed order of convergence (`d_max`, 80 -> 160 steps): **2.037** (all three
  levels agree to 1e-11 → the error is scale-invariant, as it must be for a
  self-similar contact).
* Measured `T_c` coefficient: **2.86821** vs exact 2.868492 → **-1.0e-4**.

**Verdict.** Hertz peak force error **< 3 % already at 10 steps per contact time**
(7.0e-3) and **2.8e-5 at 160 steps → PASS** against the closed form. The practical
criterion exported for the paper: `dt <= t_c/20` keeps every Hertz impact
observable inside 0.2 %, `dt <= t_c/40` inside 0.05 %.

## Table 4 — spherical-cap buoyancy kernel convergence (3 mesh levels x 5 dt)

**File:** `benchmarks/verified/dem3d_contact_friction/buoyancy_cap_convergence.csv` (15 rows).

**Method.** One floe of radius `R = 0.5 m` (`rho_p = 900`), sea water
(`rho_w = 1025`), is discretised by a cubic particle cloud with 4, 6 and 8
particles per edge (32 / 136 / 280 particles). The particle radius is
mass-corrected (`r_p = (V_sphere / (N 4pi/3))^(1/3)`), so the cloud carries
exactly the analytic displaced volume and the residual error is purely the
staircase distribution of submergence. The buoyancy kernel
`buoyancy_wet3d.submerged_fraction_sphere_tensor` (closed-form spherical cap) is
evaluated at the analytic equilibrium, and the free-float heave
`m x'' = F_b(x) - m g - c x'` is integrated at 5 `dt` levels.

**Result.**

| particles/edge | particles | rel. err `F_b` | rel. err draft | rel. err heave stiffness `K` |
|---|---|---|---|---|
| 4 | 32 | +1.19 % | -2.40 % | -60.85 % |
| 6 | 136 | -1.44 % | +1.39 % | +18.72 % |
| 8 | 280 | -1.20 % | +1.35 % | -7.96 % |

**Verdict.** The Archimedes force from the kernel is inside the 3 % band at all
three meshes (**PASS**, max 1.44 %), but it does **not** converge monotonically —
the staircase error changes sign between meshes, so a 3-level table cannot
extract an order for `F_b` (honest limitation). The heave stiffness is the
sensitive quantity (61 % at 32 particles, 8 % at 280 particles) and must not be
taken from a coarse cloud. **The `dt` axis is deliberately flat**: the buoyancy
kernel is evaluated from the instantaneous geometry every step, so it carries no
time-integration error and the five `dt` levels return identical static errors.
The heave-period column is `NaN` in all rows: the zero-crossing detector found
fewer than two upward crossings because the discrete equilibrium of the cloud
sits above the start height for the coarse mesh (reported as an instrumentation
limitation, excluded from every verdict — it is not used to claim convergence).

## Limitations / open items (honest list)

1. **`contact_damping` is not read by the particle-particle normal branch in this
   tree.** `IceDEM3D.forces` builds the normal damping from
   `restitution_coefficient` only; the `contact_damping` field feeds the tool and
   platen branches. Consequence: `tests/test_dem3d_contact_impact.py` has 5 red
   tests at the base commit (`force_law_conformance`,
   `restitution_matches_clamped_analytic`, `corrected_mapping_realises_target`,
   `contact_durations`, `timestep_convergence`) — pre-existing debt, untouched
   here. That is why Table 1 drives `restitution_coefficient` and why the
   corrected damping mapping cannot be validated end-to-end from this tree.
2. **The opt-in Hertz contact law is absent from this tree** (`hertz_*` helpers,
   `DEM3DConfig(contact_model="hertz")`): `docs/dem3d_hertz_contact_verification.md`,
   `scripts/verify_dem3d_hertz_contact.py` and `tests/test_dem3d_hertz_contact.py`
   are merged but the `dem3d.py` edits were filtered out by the merge gate
   (restored on branch `agent/m2509`, commit `8866dae`). Table 3 therefore verifies
   the **Hertz time-integration kernel** (the same semi-implicit update, against
   exact closed forms) and exports the `dt` criterion; it does not exercise the
   bonded solver's force assembly. Regenerate Table 3 against the solver once the
   Hertz branch lands.
3. Table 2's incline harness is a reduced rigid-body model (one normal spring-dashpot,
   one tangential Cundall-Strack spring, saturated `cdt` rolling torque), not the
   bonded `IceDEM3D`; it is the repository's declared reference harness for these
   coefficients, and it shares the `(k_n, e)` mapping with the solver.
4. The buoyancy `dt` axis is uninformative for a quasi-static kernel (item 4 above);
   replace it by a wave-forcing or coupled hydrostatic test if the manuscript needs
   a genuine `dt` convergence claim for the buoyancy path.
